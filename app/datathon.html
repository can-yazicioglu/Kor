IBM Z DATATHON / SECURITY, PRIVACY & RESPONSIBLE AI

Useful risk signals.
Less identity exposure.

Kör evaluates login events inside the customer environment, shows a 0–100 risk score and recommends verification or human review. It keeps short-lived evidence without retaining submitted passwords, real usernames, raw IPs or permanent device fingerprints.

AI for Good: help organizations notice account abuse while reducing unnecessary identity collection and avoiding automatic account locks that can deny legitimate users access.

A four-minute demonstration

  1. Open the employee portal. Use demo / VelaDemo!42, then the public MFA code 123456. The baseline's unavailable-threshold fallback recommends review even for normal sign-ins.
  2. Reset, replay Brute force, and inspect account failures. Reset and replay Password spraying to inspect account breadth.
  3. Reset and load the suspicious-success example, then sign in. A separate contextual safeguard requests verification without requiring preceding failed attempts. It does not change the ML score.
  4. In the security lab, test an altered decision receipt: the original verifies and the modified score fails HMAC verification.
  5. After verification, request the employee resource and the restricted audit console. Only the employee resource is authorized. Reset clears the grant, derived records and receipt key.

Evidence, including what did not work

Two synthetic tuning studies compared 54 configurations. The 21-input candidate improved session average precision from 0.709 to 0.906 and 0.684 to 0.867 in two final cohorts, but detected zero of 223 scored suspicious-success sessions. Its release remains blocked. Around one third of sessions lacked complete context; scored-only metrics must not hide that review workload.

The new context safeguard is a separately tested policy rule, not a retrained model or a claim that this ML failure has disappeared. Combined legitimate travel and device changes can trigger it. Historical evaluation cohorts are consumed; subsequent comparisons are descriptive regression checks.

The combined-context rule has a cost

On already-consumed synthetic cohorts, this separate rule matched 60/108 and 48/115 scored suspicious-success sessions. It also matched about 48–49% of benign VPN/new-device and 51–54% of benign travel/new-device sessions. Those are substantial false alarms within these groups. It therefore remains a labelled demo experiment and is disabled on trusted ingestion. These rule-only regression rates are not independent validation, and they do not qualify the blocked ML candidate.

Where IBM Z fits

The demonstrated software runs locally on this machine. No IBM Z hardware execution, Secure Execution attestation, Crypto Express key custody or Telum acceleration has been performed.

The intended deployment places inference and expiring state beside customer identity systems on Linux on IBM Z. IBM Secure Execution for Linux is a target for workload isolation; Crypto Express / managed key services are targets for protected key operations. These require platform access, configuration and verification. See IBM Z Security.

Cryptographic inventory & quantum-safe readiness

The current inventory distinguishes scrypt for the public password fixture, HMAC-SHA-256 for message/receipt authentication, SHA-256 for checksums and optional TLS 1.3 for transport. The public password-reference hashes are dictionary indexes, not secure customer-password storage. No custom cryptographic algorithm is used.

Quantum-safe migration starts with inventory, key ownership and provider replacement plans. This prototype does not implement post-quantum key exchange or signatures, and TLS 1.3 alone does not establish quantum safety. Certificate and negotiated key-exchange choices need a separate platform assessment. See IBM's quantum-safe migration guidance.
