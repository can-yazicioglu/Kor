# Trusted event contract and shadow runtime

The runtime processes **server-verified authentication events**, not browser claims about login success. It is a tenant-local, bounded prototype. A service instance represents one configured tenant; an incoming event cannot select another tenant. The interactive demo uses an explicitly synthetic identity-provider adapter. A real adapter must validate authentication and derive permitted context inside the customer's environment.

The original 17-column CSV and 11-feature model are unchanged. The runtime event contract is a separate transport format. It does not accept passwords, username/email/IP values, password hashes, target labels, attack labels or arbitrary metadata.

## Python API

```python
from src.runtime.risk import RiskEngine, EventValidationError, CapacityError, validate_event

checked_event = validate_event(event)  # Structural validation before transport.
engine = RiskEngine(model, policy, now=time.time, event_mode="trusted_idp")
result = engine.ingest(checked_event)
aggregate = engine.snapshot()
review_summary = engine.feedback(event_id, "normal")  # or "suspicious"
engine.reset()
```

`event_mode` defaults to `synthetic_demo`; the service controls it. `policy_ready` means that model/calibration artifacts are valid, **not** that feasible action thresholds were selected. Runtime imports require only the Python standard library. The host service must serialize requests with a lock and verify the policy's model-file SHA-256 at startup using `load_policy`; dictionary-level validation cannot recover the original JSON file's byte representation.

`validate_event` returns an independent copy with canonical UUIDs and exactly the public event fields; it never adds internal timestamps or accepts extra sensitive fields. It checks structure without changing engine state. Ingestion independently validates structure, time, replay, capacity and session binding against the receiving server's clock/state. A sending adapter should call the public validator before opening a network connection.

## Exact event fields

Every field below is required. Extra fields are rejected before state mutation.

| Field | Contract |
| --- | --- |
| `event_id` | Canonical nonzero UUID, generated by the trusted producer. Duplicate IDs within retention are rejected. |
| `event_ts_utc` | Valid ISO-8601 UTC timestamp ending in `Z`, with optional 1–6 fractional digits. |
| `account_token` | `acct_` followed by 32 lowercase hexadecimal characters; random or customer-local opaque identity-provider mapping. |
| `session_token` | Canonical nonzero UUID, generated by the trusted producer. Bound to one account within retained state; cross-account reuse is rejected. |
| `source_token` | `source_` or `src_` followed by 32 lowercase hexadecimal characters. Short-lived customer-local source correlation, shared where needed across accounts. |
| `event_type` | `login_success`, `login_failure`, `mfa_success`, or `mfa_failure`. |
| `auth_method` | `password`, `passkey`, `totp`, or `none`, with the event constraints below. |
| `features` | An object containing exactly the existing 11 baseline feature names. Values may be `null`; unknown history is never fabricated. |
| `password_in_blocklist` | `0`, `1`, or `null`; separate trusted local-check result, never a trained model feature. |
| `password_near_blocklist` | `0`, `1`, or `null`; mutually exclusive with exact match; both flags are unknown together. |

Token-format validation does not prove anonymity or random generation. The producer must never encode a real identity or address into these fields. The runtime does not accept a raw IP to create a source token. Source/session token rotation is the adapter's responsibility. The included demo adapter rotates sessions after 120 seconds and source tokens after 120 seconds of inactivity; keeping an active source correlated avoids fabricating distributed-source evidence merely through periodic rotation. All demo state also has an absolute five-minute lifetime.

MFA events require `totp` or `passkey`. Login events accept `password`/`passkey`, or `none` only for failure. A successful login cannot use `none`. Non-password events must supply both password flags as `null`. MFA evidence requires an earlier successful login in the **same account and session**. A passkey login can directly establish strong verification. This contract does not itself validate a password, TOTP or WebAuthn assertion; trusted adapters must do that first.

## Causal ingestion and retention

Events are sequential, with nondecreasing timestamps across the instance. Equal timestamps use ingestion order. Late events, **any timestamp ahead of the receiving server clock**, and events at least five minutes old are rejected. A future event may be retried once the server clock reaches its timestamp; it never advances the ordering watermark or blocks present-time events for other accounts. The HTTP signature's freshness tolerance is a separate transport check and does not authorize future event times. Replays, cross-account reuse of a retained session UUID, and invalid input do not update counters, verification or risk state.

Each engine retains at most **5,000 events for five minutes**. Full capacity raises `CapacityError` rather than silently discarding recent history. The hosting service additionally reserves separate 1,000-demo-event and 4,000-trusted-event budgets within a process-wide 5,000-event limit. Expiry removes raw event references, feedback targets and inactive session state. `reset()` clears the instance. These are application reference-release guarantees, not physical memory/swap erasure guarantees.

Two-minute features use `(t−120 seconds,t]`: an event exactly 120 seconds earlier is excluded. Only login success/failure contributes to login-attempt counts; MFA checks are separate. The runtime recomputes:

- Same-account `attempts_2m`, regardless of cookie/session changes.
- Same-source `distinct_accounts_2m`, across accounts.
- Same-account `distinct_sources_2m` and failure count.
- Same-account consecutive failures and the count preceding a successful login.
- Same-session MFA failure count.

The same events also produce these additional **descriptive signals**. They are not extra model inputs or numeric score bonuses.

| Signal | Meaning within `(t−120 seconds,t]` |
| --- | --- |
| `account_failure_ratio_2m` | Failed login attempts divided by all login attempts for this account. |
| `source_failure_ratio_2m` | Failed login attempts divided by all login attempts from this transient source, across accounts. |
| `source_failed_accounts_2m` | Distinct accounts with at least one failed login from this source. |
| `source_successful_accounts_2m` | Distinct accounts with at least one successful login from this source; may overlap failed accounts. |
| `distinct_failed_sources_2m` | Distinct sources with at least one failed login against this account; successful sources alone do not count. |
| `account_max_failures_per_source_2m` | Largest failed-attempt count from any single source against this account, or zero without failures. |
| `median_attempt_gap_seconds` | Median gap between consecutive same-account login events, only with at least three attempts. |
| `burst_ratio` | Fraction of consecutive same-account login gaps of at most five seconds, only with at least three attempts. |
| `attempt_gap_support` | Number of observed consecutive gaps, equal to `max(attempts_2m−1,0)`. |
| `derived_window_complete` | Whether the observation window is complete under the runtime's stated stream assumptions. |

Ratios with no login denominator and gap statistics with insufficient support are `null`, never a fabricated zero. Equal-timestamp login attempts have zero-second gaps. MFA events do not add login attempts or gaps. During trusted startup, ratios and gaps describe only the observed sample; they are **not lower bounds** on complete-window ratios. Completeness is explicit. The ratio-based source rule waits for a complete observation window; count-only evidence can still justify review from observed lower bounds. Gap statistics have no policy effect in this version.

`attempts_1h` remains a trusted upstream aggregate. A supplied value smaller than the observed account-attempt lower bound is rejected; `null` stays unknown. `failed_ratio_24h` remains a range-checked trusted aggregate because a five-minute runtime cannot reconstruct or verify a complete 24-hour denominator. Profile, ASN, network and device context remain trusted adapter inputs. The runtime never assumes a real 30-day history.

### Trusted-stream startup coverage

In `trusted_idp` mode, the engine cannot know which events happened before it started. Its first observed counts are therefore **lower bounds**, even when every supplied feature is present. After construction or explicit `reset()`, numeric scoring stays unavailable until a full 120-second observation window has elapsed. The elapsed interval is `min(server_now, event_timestamp) - observation_start`, capped to the window length: a future-dated event cannot finish warmup early, and a backfilled timestamp cannot borrow wall-clock coverage it did not have.

During warmup, `score=null`, `data_quality.level="insufficient"`, `data_quality.window_complete=false`, and `signals.counts_are_lower_bounds=true`. The result includes a specific startup-coverage reason. `data_quality.observation_window_seconds` exposes the observed interval. At exactly 120 seconds, scoring is possible only if the remaining history/features and calibration are also available. Empty/expired event storage does not reset observation start; an explicit engine reset does.

The synthetic demo has a different, explicit assumption: its invented stream starts empty. It can score immediately and reports `window_basis="synthetic_stream_starts_empty"`; this assumption must never be transferred to a real identity-provider stream. The trusted mode does not use the demo's invented prior outcomes.

Completing warmup assumes that the configured producer delivers a complete, ordered stream. It does not prove delivery completeness, detect omitted events or certify upstream stream health. Such health/provenance signals require a separately defined adapter contract before any production reliability claim.

## Numeric risk, contextual policy and verification

`score` is the **current calibrated model score**, and `base_score` is the original model's uncalibrated integer score. Calibration is fitted on a synthetic validation partition, so the resulting number is not an established real-world compromise probability. `peak_score` preserves the highest observed score for the retained active session; an unscored event does not turn an earlier peak into zero.

Missing required context, incomplete trusted-stream startup coverage, unavailable/corrupt artifacts or invalid calibration produce `score=null` and a review recommendation. Missing action thresholds do **not** remove an otherwise available calibrated number: the result is scored with limited decision support and explicit human review. There is no fallback to the old arbitrary 30/70 thresholds.

Password-reference exact/near flags are displayed as **credential weakness evidence**, without +25/+10 numeric additions. The earlier additive demonstration policy is superseded for this runtime. A failed attempt with a weak submitted value does not identify the actual account password. A match does not establish an account breach; a miss does not prove safety.

The following transparent heuristics may raise the recommended action while leaving the calibrated number unchanged:

| Corroborating observation within two minutes | Minimum recommendation |
| --- | --- |
| At least eight failures against one account | Review |
| At least five failures against one account, involving at least three distinct sources that each failed | Review |
| At least eight distinct accounts with failures from one source, and at least 80% of that source's login attempts failing, with a complete observation window | Review |
| At least three MFA failures in the same account/session | Review |
| Success after at least three failures plus new/unfamiliar or unusual time/location context | MFA |
| Successful password authentication after at least two failures, with exact/near weakness and a new device on an unfamiliar network | Review |

These thresholds are explainable prototype rules, not learned probabilities or production-validated detection guarantees. VPN, travel, device novelty, a reference match, or a few ordinary password mistakes do not independently trigger these sequence rules. Numeric model actions can still vary and must be evaluated separately.

Sequence policy `els-contextual-shadow-v2` distinguishes a busy shared office source from failure-dominated account breadth, and counts failing sources separately from successful sources. Successful traffic does not whitelist repeated failures against one account or distributed failures. This reduces two specific ambiguity cases by construction; it is **not evidence of an empirical false-positive reduction**. A spray mixed with enough successful traffic may fall below the source rule, so this prototype rule is not a complete attack detector.

Verification is one of `not_verified`, `password_verified`, `mfa_verified`, or `passkey_verified`. Strong verification is independent evidence. It does not erase peak risk or active corroborated sequence evidence. Evidence is isolated by account and session; another account's failure cannot revoke or grant verification. Recent session sequence recommendations remain visible after a successful MFA event.

## Result shape

An ingestion result includes:

- `event_id`, `score`, `peak_score`, `base_score` and `reasons`.
- `action`: `monitor`, `mfa`, or `review`, with an English `action_label`.
- `data_quality.level`: `sufficient`, `limited`, or `insufficient`; missing feature names, feature coverage, history provenance, model/calibration readiness and action-threshold availability are separate fields. `observation_window_seconds`, `window_complete` and `window_basis` distinguish startup lower bounds from the explicitly fresh synthetic stream.
- `signals`: observed rolling evidence; `success_after_failures` is boolean and `prior_failures_before_success` preserves the count.
- `credential_risk.status`: `checked` or `unknown`; `match`: `exact`, `near`, `none`, or `unknown`; evidence scope and contextual escalation are explicit.
- `verification`, `policy_version`, `sequence_policy_version` and `model_version` (the string `unavailable` when needed).
- `shadow_mode=true` and `enforced=false`.

No account/source token or feature values are copied into risk explanations. The only identity returned by ingestion is the event UUID needed for review correlation. The trusted service is advisory: these recommendations do not automatically lock accounts, trigger MFA, deny access or certify that a session is safe.

## Independent feedback and aggregate monitoring

`snapshot()` returns aggregates only: score coverage/bins, action frequency, authentication-outcome counts, fixed context subgroups, missing-context rates and a descriptive earlier/later comparison of the retained window. It does not return event/account/session/source IDs or raw events. Window changes are operational observations, **not a validated drift detector**.

`sequence_contexts` adds overlapping aggregate groups for the new checks. Each includes event counts, final-action alerts, sequence-only alerts, unscored counts and independently supplied human feedback. They are descriptive contexts, never automatic normal/suspicious labels:

| Aggregate context | Condition in the event's observed window |
| --- | --- |
| `shared_source_success_dominant` | At least eight accounts succeeded from the source, with a source failure ratio below 0.5. |
| `concentrated_account_failures` | At least five account failures, all from one failing source. |
| `multisource_recovery` | Success immediately after account failures, at least three observed sources, fewer than three failing sources. |
| `distributed_account_failures` | At least five account failures across at least three failing sources. |
| `failure_dominant_source` | At least eight failed accounts and a source failure ratio of at least 0.8 in a complete window. |

The source-success group and recovery group do not assert benign intent. The failure groups do not establish compromise. Separate sequence-only alert counts prevent unavailable model thresholds or unrelated model recommendations from being mistaken for sequence-rule behavior.

Ground truth comes only from explicit `feedback(event_id, "normal" | "suspicious")` by an authorized independent reviewer. Successful login, MFA completion, a model score or a heuristic alert never becomes a target label automatically. Correcting feedback replaces the prior label for that event. Expired events cannot be reviewed through the bounded runtime.

Reported feedback confusion counts measure **recommended actions** against retained human labels, including an explicit count of unscored reviewed events. Empty denominators yield `null`, not perfect performance. Context subgroups overlap and must not be summed as disjoint populations. These small, selected observations are not unbiased real-world model-performance estimates.

## Fresh adversarial checks

`tests/test_runtime_risk.py` uses new in-memory test fixtures, never training examples or additional baseline data. It covers normal VPN/travel/new-device contexts, ordinary wrong passwords, cold start, cookie/source rotation, distributed failures, spraying, success after failures, MFA bypass/isolation, preserved peaks, exact window boundaries, replay/late/future/schema rejection, capacity, expiry, independent feedback and fail-closed calibration/threshold behavior. Trusted startup checks cover 0/119/120 seconds, future/backfilled timestamps, missing history after warmup, idle expiry and explicit reset.

Additional challenge fixtures cover a shared office source with many successful accounts and one user's mistakes; failed-account breadth and the exact 0.8 source-ratio boundary; successful sources that must not inflate distributed-failure counts; repeated/distributed failures that remain visible alongside legitimate traffic; same-account gap statistics and empty denominators; aggregate feedback without automatic labels; cross-account session reuse; and a one-millisecond future event that must not poison global ordering. These are expected-behavior tests, not a representative traffic benchmark.

```bash
.venv/bin/python -m unittest discover -s tests -p 'test_runtime_risk.py' -v
```

Some tests use explicitly artificial, resealed action thresholds solely to isolate sequence logic. They are never exported, trained, deployed or reported as empirical calibration quality. The delivered validation-selected policy is checked separately, including infeasible-threshold behavior.
